## 1. Sprint Goal

Deliver the Requester-facing half of TokTickIT: a person can identify themselves
through a temporary development selector, raise an IT support ticket with
supporting files, receive an official Ticket Number generated by the backend, and
then find, filter, and inspect only their own tickets. The sprint also
establishes the Zen Green visual system and the reusable form, list, badge,
validation, and responsive conventions that Labs 3 and 4 will build on rather
than reinvent.

---

## 2. Stakeholder Request Interpretation

The IT department wants to stop collecting support requests informally and start
receiving them through a real system. My reading of the request:

- The **ticket intake path must be complete end to end** — describe the problem,
  classify it, attach evidence, submit, and get back an official number that
  proves the request was recorded.
- **Ownership is the security story of this sprint.** Login does not exist yet,
  but the system must already behave as if identities were real: one Requester
  must never see or touch another Requester's ticket, and that must be enforced
  by the server, not by hiding buttons.
- The **Development Requester selector is scaffolding, not a feature.** It exists
  so multi-user ownership can be tested before Lab 3 adds authentication. It must
  be labelled as such on screen so no one mistakes it for a login.
- **Visual consistency is a deliverable, not a nice-to-have.** The Zen Green
  theme and the component rules are being specified now precisely so later
  sprints inherit them.
- The stakeholder described *behaviour*, not *engineering*. Field lengths, the
  ticket-number format, query-parameter names, storage strategy, and error
  semantics were left open and are decided in §11.

## 3. Scope

### 3.1 Included

| Area | Delivered |
|------|-----------|
| Development Requester context | Selection screen, active-requester loading, persisted selection, Change Requester, reload on switch |
| Create Ticket | Full form, reference data from DB, validation, attachment upload, backend-generated Ticket Number |
| My Tickets | Owned-only list with search, filter, sort, pagination, and all empty/loading/error states |
| Ticket Detail | Read-only ticket view with attachment list |
| Attachment lifecycle | Upload, metadata, download, soft removal with reason |
| Ownership protection | Server-enforced on every ticket and attachment route |
| Zen Green UI foundation | Colour tokens, form/list/badge components, responsive layout at three breakpoints |
| Testing | Unit, API, UI component, UI style, responsive, and E2E coverage |

### 3.2 Explicitly excluded

- **Authentication and security** — login, logout, passwords, hashing, sessions,
  tokens, real identities, role-based authorization. The Development Requester
  selector is a testing mechanism and is not secure authentication.
- **IT Staff workflow** — staff dashboard, queue, claiming or reassigning
  tickets, IT Priority, and any other ticket-owner function.
- **Collaboration and work tracking** — Public Comments, Internal Notes,
  Actions Taken.
- **Ticket lifecycle after creation** — any status change beyond the initial
  `New`, including resolving, closing, reopening, and cancelling.
- **Administration** — management of users, Requesters, roles, or reference data.

## 5. Business Rules

### 5.1 Ticket identity and defaults

| ID | Rule |
|----|------|
| **BR-01** | The official Ticket Number is generated by the backend and must be unique. |
| **BR-02** | A new Ticket begins with Current Status `New`. |
| **BR-14** | The Ticket Number uses the format `TKT-YYYY-NNNNNN`, where `YYYY` is the creation year and `NNNNNN` is a zero-padded sequence that restarts each year and is unique within that year. |
| **BR-15** | Ticket Date is set by the server at the moment of successful creation and is never accepted from the client. |
| **BR-16** | Ticket Number, Ticket Date, and Current Status are read-only. Values supplied by the client for these fields are ignored. |
| **BR-17** | Every Ticket records `createdAt` and `updatedAt` maintained by the system. |
| **BR-18** | A Ticket's Requester is taken from the currently selected Development Requester and is never accepted as free text. |

### 5.2 Development Requester selection and switching

| ID | Rule |
|----|------|
| **BR-03** | Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication. |
| **BR-19** | A Requester must be selected before Create Ticket, My Tickets, or Ticket Detail can be used. Any attempt to reach them without a selection returns the user to the selection screen. |
| **BR-20** | The selector loads only active Requesters from PostgreSQL. Requester lists are never hard-coded in the frontend. |
| **BR-21** | The selected Requester is stored in the browser (`localStorage`) and survives a page reload. |
| **BR-22** | Switching Requester reloads all Requester-scoped data. Data belonging to the previous Requester must never remain on screen. |
| **BR-23** | If loading the Requester list fails, a safe error state with a retry action is shown and the application cannot be entered. |
| **BR-24** | If no active Requester exists, an explanatory empty state is shown instead of an empty dropdown. |
| **BR-25** | If the stored Requester is later found to be inactive or missing, the stored selection is cleared and the user is returned to the selection screen. |

### 5.3 Ownership

| ID | Rule |
|----|------|
| **BR-26** | Ownership is enforced by the backend on every request. Hiding controls in the UI is never the protection mechanism. |
| **BR-27** | My Tickets returns only Tickets belonging to the selected Requester. |
| **BR-28** | A request for a Ticket the selected Requester does not own is rejected with **404 Not Found** — the same response as a Ticket that does not exist — so the API never reveals that another Requester's Ticket exists. |
| **BR-29** | Attachments are reachable only through a Ticket the selected Requester owns. Guessing an attachment id directly is rejected under BR-28. |
| **BR-30** | Uploading and removing attachments is permitted only on the selected Requester's own Tickets. |

### 5.4 Search, filtering, sorting, pagination

| ID | Rule |
|----|------|
| **BR-31** | Search matches Ticket Number and Summary, case-insensitively, on a trimmed search term. |
| **BR-32** | The list is filterable by Category, Related System, Requested Priority, and Current Status. |
| **BR-33** | The list is sortable by Ticket Date, Ticket Number, and Last Updated. The default is Ticket Date, newest first. |
| **BR-34** | Every sort applies `id` descending as a secondary key so ordering is deterministic when the primary key ties. |
| **BR-35** | Permitted page sizes are 10, 20, and 50. The default is 10. |
| **BR-36** | Invalid query parameters (page below 1, unknown sort field, page size outside the permitted set) fall back to the documented default instead of failing the request. |
| **BR-37** | Every list response includes `page`, `pageSize`, `totalItems`, and `totalPages`. |
| **BR-38** | Search, filter, sort, and pagination always compose with ownership. Filtering can never widen the result set beyond the selected Requester's own Tickets. |

### 5.5 Validation and duplicate submission

| ID | Rule |
|----|------|
| **BR-39** | Summary is required, trimmed before validation, and must be 5–150 characters. |
| **BR-40** | Description is required, trimmed before validation, and must be 20–5000 characters. |
| **BR-41** | Category, Related System, and Requested Priority are required and must reference rows that exist and are active. |
| **BR-42** | Validation runs on both the frontend and the backend. The frontend improves feedback; the backend is authoritative. |
| **BR-43** | The Submit button is disabled and shows a busy state while a submission is in flight, preventing duplicate tickets from repeated clicks. |
| **BR-44** | Validation messages appear beneath the field they concern. A single unexplained banner at the top of the form is not acceptable. |
| **BR-45** | Values the user entered are preserved when validation fails. |

### 5.6 Failure behaviour

| ID | Rule |
|----|------|
| **BR-46** | When an API call fails, the UI shows a comprehensible message and preserves every value already entered so the user can retry without retyping. |
| **BR-47** | Error messages returned to the client never contain stack traces, SQL, or internal file paths. |
| **BR-48** | If the Ticket is created but an attachment upload fails, the Ticket is kept. The response states which files failed, and the user can attach them again from Ticket Detail. Ticket creation and attachment upload are therefore **not** a single transaction — this is a deliberate compensation strategy, justified in §11. |

### 5.7 Attachments

| ID | Rule |
|----|------|
| **BR-04** | Permitted types are JPG/JPEG, PNG, WEBP, and PDF only. |
| **BR-05** | Maximum size is 5 MB per file. |
| **BR-06** | A Ticket may hold at most five active attachments. |
| **BR-07** | Removal is always soft removal. Rows are never deleted from the database. |
| **BR-08** | A removed attachment remains visible as metadata but can never be downloaded or previewed. |
| **BR-49** | Each attachment stores original filename, stored filename, MIME type, size in bytes, upload timestamp, and uploading Requester. |
| **BR-50** | The stored filename is generated by the server (UUID plus a validated extension). A client-supplied filename is never used as a path segment, which prevents path traversal. |
| **BR-51** | File type is validated against the detected MIME type, not the filename extension alone. |
| **BR-52** | A rejected file produces a specific reason: unsupported type, file too large, or attachment limit reached. |
| **BR-53** | Removal requires an explicit confirmation step and a removal reason of 3–200 characters. |
| **BR-54** | Removal records the removal timestamp, the removing Requester, and the reason. |
| **BR-55** | Removed attachments stay in the list, clearly badged as Removed with their reason, and expose no download control. |
| **BR-56** | Removed attachments do not count toward the five-attachment limit in BR-06. |

### 5.8 Empty and no-results states

| ID | Rule |
|----|------|
| **BR-57** | "No tickets yet" and "no tickets match your filters" are distinct states with distinct messages. The first invites creating a first ticket; the second invites clearing filters. |
| **BR-58** | A Clear filters action is available whenever the no-results state is shown. |

### 5.9 Ticket Detail access

| ID | Rule |
|----|------|
| **BR-59** | Every Ticket field on the Detail screen is read-only in Lab 2. |
| **BR-60** | A non-existent Ticket and another Requester's Ticket produce identical responses, per BR-28. |

### 5.10 Seed data

| ID | Rule |
|----|------|
| **BR-09** | The seed is idempotent — running it repeatedly creates no duplicates. |
| **BR-10** | Categories seeded: Account and Access, Hardware, Software, Network. |
| **BR-11** | At least six Related Systems are seeded: Email, Campus Wi-Fi, VPN, LEB2 App, Grade Submission App, Printer, Corporate Laptop. |
| **BR-12** | At least four active and at least one inactive Development Requester are seeded. |
| **BR-13** | Inactive Requesters never appear in the selector. |

### 5.11 Transition to Lab 3

| ID | Rule |
|----|------|
| **BR-61** | The selection screen states on screen that it is not a login and that authentication arrives in Lab 3. |
| **BR-62** | No password, session, token, or role exists in Lab 2 code or schema. |
| **BR-63** | `RequesterUser` carries a unique `email` so Lab 3 can attach credentials to it without restructuring the table or rewriting migrations. |

- Labels sit above controls with consistent weight and spacing.
- Required fields show a red asterisk; the asterisk never replaces the message.
- Inputs share one height; Description is taller and resizes only within the layout.
- Buttons carry visible text; icons support text but never replace it.
- Every icon-only control has an accessible label and a tooltip.
- Disabled controls are visually distinct and cannot be activated.
- Focus indicators stay visible for keyboard users.
- Submit shows a busy state and is disabled while a request is in flight.
- Validation messages sit next to their field.
- The success state shows the generated Ticket Number and the next action.
- Status and Priority badges use one shared component; meaning never rests on colour alone.

### 6.5 Responsive behaviour

| Viewport | Behaviour |

| Tablet 768–991 px | Two columns where practical; Summary and Description keep width |
| Mobile < 768 px | Fields stack; touch-friendly buttons; ticket list becomes cards; no horizontal page scrolling |
| All sizes | No clipped labels, overlapping messages, hidden buttons, or unreadable attachment names |

## 7. Data Changes

### 7.1 Models

```prisma
enum RequestedPriority { LOW MEDIUM HIGH }
enum TicketStatus     { NEW }

model RequesterUser {
  id        Int      @id @default(autoincrement())
  name      String
  email     String   @unique
  isActive  Boolean  @default(true)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
  tickets   Ticket[]
  uploaded  Attachment[] @relation("UploadedBy")
  removed   Attachment[] @relation("RemovedBy")
}

model Category {
  id        Int      @id @default(autoincrement())
  name      String   @unique
  isActive  Boolean  @default(true)
  createdAt DateTime @default(now())
  tickets   Ticket[]
}

model RelatedSystem {
  id        Int      @id @default(autoincrement())
  name      String   @unique
  isActive  Boolean  @default(true)
  createdAt DateTime @default(now())
  tickets   Ticket[]
}

model Ticket {
  id                Int               @id @default(autoincrement())
  ticketNumber      String            @unique
  requesterId       Int
  categoryId        Int
  relatedSystemId   Int
  summary           String            @db.VarChar(150)
  description       String            @db.Text
  requestedPriority RequestedPriority
  currentStatus     TicketStatus      @default(NEW)
  ticketDate        DateTime          @default(now())
  createdAt         DateTime          @default(now())
  updatedAt         DateTime          @updatedAt

  requester     RequesterUser @relation(fields: [requesterId],     references: [id])
  category      Category      @relation(fields: [categoryId],      references: [id])
  relatedSystem RelatedSystem @relation(fields: [relatedSystemId], references: [id])
  attachments   Attachment[]

  @@index([requesterId, ticketDate(sort: Desc)])
  @@index([requesterId, currentStatus])
}

model Attachment {
  id               Int      @id @default(autoincrement())
  ticketId         Int
  originalFilename String
  storedFilename   String   @unique
  mimeType         String
  sizeBytes        Int
  uploadedAt       DateTime @default(now())
  uploadedById     Int
  removedAt        DateTime?
  removedById      Int?
  removalReason    String?  @db.VarChar(200)

  ticket     Ticket        @relation(fields: [ticketId],     references: [id])
  uploadedBy RequesterUser @relation("UploadedBy", fields: [uploadedById], references: [id])
  removedBy  RequesterUser? @relation("RemovedBy", fields: [removedById],  references: [id])

  @@index([ticketId, removedAt])
}

model TicketNumberSequence {
  year      Int @id
  lastValue Int @default(0)
}
```

### 7.2 Relationships

One Requester owns many Tickets · one Ticket belongs to one Requester · one
Ticket holds many Attachments · one Category serves many Tickets · one Related
System serves many Tickets. Attachments additionally reference the Requester who
uploaded them and, once removed, the Requester who removed them.

### 7.3 Justified design decisions

**Composite index `(requesterId, ticketDate DESC)` — the load-bearing decision.**
Every My Tickets query filters by `requesterId` (BR-27) and sorts by `ticketDate`
descending (BR-33). A single-column index on `requesterId` would still force
PostgreSQL to sort the matched rows on every page request. The composite index
lets the planner satisfy both the filter and the ordering from one index scan,
so pagination stays cheap as ticket volume grows. `(requesterId, currentStatus)`
supports the most selective filter in BR-32.

**Soft removal by nullable timestamp.** `removedAt IS NULL` means active. This
keeps one row per attachment for its whole life, satisfies BR-07 and BR-55, and
makes both the five-attachment count (BR-06, BR-56) and the download guard
(BR-08) a single predicate rather than a status column that could drift.

**`TicketNumberSequence` as a table rather than a Postgres sequence.** BR-14
restarts numbering each year, which a plain sequence cannot express. A row per
year, updated inside the creation transaction, makes the reset explicit and
keeps allocation atomic under concurrency.

**`TicketStatus` declared with only `NEW`.** Lab 2 excludes every status change,
so declaring unreachable values now would be speculative. PostgreSQL adds enum
values with `ALTER TYPE ... ADD VALUE`, which needs no data migration, so Lab 3
can extend this cheaply.

### 7.4 Migration plan

One migration, `lab2_requester_ticketing`, which adds `isActive` to the existing
`Category` table, creates `RequesterUser`, `RelatedSystem`, `Ticket`,
`Attachment`, and `TicketNumberSequence`, and creates both enums. The Lab 1
`Category` rows survive: `isActive` is added with default `true`.

### 7.5 Seed

Idempotent `upsert` on each natural key (BR-09): four Categories, seven Related
Systems, four active Requesters, one inactive Requester.

## 8. API Contract

Full detail lives in [`api-spec.md`](./api-spec.md).

### 8.1 Requester context

Every Requester-scoped request carries the header `X-Requester-Id: <id>`. A
missing, malformed, unknown, or inactive value returns **401** with
`{ "error": "No Development Requester selected" }`. This header is deliberately
shaped like an authentication header so Lab 3 can replace it with a real token
without redesigning any route.

### 8.2 Endpoints

| Method | Path | Purpose | Success |
|--------|------|---------|---------|
| GET | `/api/health` | Liveness (carried over from Lab 1) | 200 |
| GET | `/api/requesters` | Active Requesters for the selector | 200 |
| GET | `/api/categories` | Active Categories | 200 |
| GET | `/api/related-systems` | Active Related Systems | 200 |
| POST | `/api/tickets` | Create one Ticket | 201 |
| GET | `/api/tickets` | The selected Requester's Tickets, paginated | 200 |
| GET | `/api/tickets/:id` | One owned Ticket with attachments | 200 |
| POST | `/api/tickets/:id/attachments` | Upload one attachment | 201 |
| GET | `/api/tickets/:id/attachments` | Attachment metadata for an owned Ticket | 200 |
| GET | `/api/attachments/:id/download` | Download an active attachment | 200 |
| DELETE | `/api/attachments/:id` | Soft-remove an attachment | 200 |

### 8.3 Ticket list query contract

```
GET /api/tickets?search=&categoryId=&relatedSystemId=&priority=&status=
                &sort=ticketDate&order=desc&page=1&pageSize=10
```

| Parameter | Values | Default | Invalid input |
|-----------|--------|---------|---------------|
| `search` | free text, trimmed | none | treated as absent |
| `categoryId`, `relatedSystemId` | integer | none | ignored (BR-36) |
| `priority` | `LOW`\|`MEDIUM`\|`HIGH` | none | ignored |
| `status` | `NEW` | none | ignored |
| `sort` | `ticketDate`\|`ticketNumber`\|`updatedAt` | `ticketDate` | falls back to default |
| `order` | `asc`\|`desc` | `desc` | falls back to default |
| `page` | integer ≥ 1 | 1 | falls back to 1 |
| `pageSize` | 10\|20\|50 | 10 | falls back to 10 |

Response:

```json
{
  "items": [ { "id": 1, "ticketNumber": "TKT-2026-000001", "summary": "...",
               "category": { "id": 1, "name": "Hardware" },
               "relatedSystem": { "id": 7, "name": "Corporate Laptop" },
               "requestedPriority": "MEDIUM", "currentStatus": "NEW",
               "ticketDate": "2026-08-26T09:14:00.000Z",
               "updatedAt": "2026-08-26T09:14:00.000Z" } ],
  "page": 1, "pageSize": 10, "totalItems": 23, "totalPages": 3
}
```

### 8.4 Create Ticket

Request `POST /api/tickets`:

```json
{ "categoryId": 1, "relatedSystemId": 7, "requestedPriority": "MEDIUM",
  "summary": "Laptop battery drains quickly",
  "description": "The battery drops from 100% to 20% in about an hour ..." }
```

Response `201`:

```json
{ "id": 1, "ticketNumber": "TKT-2026-000001", "currentStatus": "NEW",
  "ticketDate": "2026-08-26T09:14:00.000Z", "requesterId": 1 }
```

Validation failure `400`:

```json
{ "error": "Validation failed",
  "fields": { "summary": "Summary must be 5–150 characters." } }
```

### 8.5 Status codes

| Status | Used when |
|--------|-----------|
| 200 | Successful retrieval, download, or soft removal |
| 201 | Ticket created; attachment uploaded |
| 400 | Validation failure; missing removal reason; unknown category or related system |
| 401 | Missing, unknown, or inactive `X-Requester-Id` |
| 404 | Ticket or attachment does not exist **or** is not owned (BR-28) |
| 409 | Attachment limit of five reached (BR-06); attachment already removed |
| 413 | Upload exceeds 5 MB (BR-05) |
| 415 | Unsupported file type (BR-04) |
| 500 | Unexpected server error, reported safely (BR-47) |

### 8.6 Error shape

Every error responds as `{ "error": string, "fields"?: object }` and never
carries internal detail (BR-47).

## 9. Acceptance Criteria

### Requester context

| ID | Criterion |
|----|-----------|
| **AC-01** | Given the app is opened with no selection, when the user loads any ticket screen, then the Development Requester Selection screen is shown. |
| **AC-02** | Given active and inactive Requesters exist, when the selector loads, then only active Requesters appear. |
| **AC-03** | Given a Requester is selected, when the page is reloaded, then the same Requester is still selected and the shell shows their name. |
| **AC-04** | Given Requester A is selected, when the user chooses Change Requester and picks Requester B, then B's name is shown and no data belonging to A remains on screen. |
| **AC-05** | Given the requester API fails, when the selection screen loads, then a safe error message and a retry action are shown and the app cannot be entered. |
| **AC-06** | Given no active Requester exists, when the selection screen loads, then an explanatory empty state is shown rather than an empty dropdown. |

### Ticket creation

| ID | Criterion |
|----|-----------|
| **AC-07** | Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed. |
| **AC-08** | Given a Ticket was created, when its record is read, then `requesterId` matches the selected Requester and `currentStatus` is `NEW`. |
| **AC-09** | Given two Tickets are created in the same year, when their numbers are compared, then both match `TKT-YYYY-NNNNNN` and are unique. |
| **AC-10** | Given the Create Ticket screen loads, when reference data is rendered, then Categories and Related Systems come from the database, not hard-coded values. |
| **AC-11** | Given Summary is empty, when the Requester submits, then a message appears beneath the Summary field and no API call is made. |
| **AC-12** | Given Summary is 4 characters, when the form is submitted directly to the API, then 400 is returned with a field-level message. |
| **AC-13** | Given a submission is in flight, when the Requester clicks Submit again, then the button is disabled and only one Ticket is created. |
| **AC-14** | Given the backend is unavailable, when the Requester submits, then a safe error message is shown and every entered value is preserved. |

### My Tickets

| ID | Criterion |

## 11. Assumptions and Decisions

| # | Decision | Reasoning |
|---|----------|-----------|
| **D-01** | Ticket Number format `TKT-YYYY-NNNNNN` | Readable and sortable; the year makes age obvious when a Requester quotes a number to IT; six digits leave room for a million tickets a year. Requires the sequence table in §7.1. |
| **D-02** | Priority values `LOW`, `MEDIUM`, `HIGH` | The handout's own example JSON uses `"MEDIUM"`. Three levels is the smallest set that lets a Requester express urgency; adding `URGENT` invites everyone to pick it, and IT Priority in a later lab is the real triage signal anyway. |
| **D-03** | Attachments stored on local disk under `server/uploads/`, database holds metadata only | Keeps the database small and backups fast, and matches what a single-server lab deployment can actually verify. Row-level `bytea` would bloat every query plan for no benefit at this scale. |
| **D-04** | Summary 5–150 characters | 150 fits one list row at desktop width without truncation, so the list column in §6.3 never needs an ellipsis; 5 rejects placeholder entries like "help". |
| **D-05** | Description 20–5000 characters | 20 forces more than a restatement of the Summary; 5000 comfortably holds a log paste while bounding the payload. |
| **D-06** | Cross-Requester access returns **404**, not 403 | 403 confirms the resource exists, which leaks information about other Requesters. Returning the same 404 as a missing Ticket reveals nothing. The handout asks for "safe errors" and says the data "is not returned". |
| **D-07** | Requester context travels in the `X-Requester-Id` header | A header is where an identity belongs. In Lab 3 it becomes `Authorization`, and no route signature changes. Putting the id in the query string or body would spread identity across every request shape and make it look like ordinary data. |
| **D-08** | Ticket creation and attachment upload are separate operations (BR-48) | A Requester who wrote a long Description should not lose it because one file failed. Keeping the Ticket and reporting the failed files is kinder and matches how the Detail screen can recover. |
| **D-09** | Removal reason is mandatory, 3–200 characters | The handout requires "soft removal with reason" in the Part 8 evidence, so the reason is treated as required rather than optional. |
| **D-10** | Selected Requester stored in `localStorage` | It must survive reload (BR-21) without a server session, which Lab 2 excludes. It is explicitly not a security boundary — the server re-validates the id on every request. |
| **D-11** | Client routing uses `react-router-dom` | Decided during Issue #12, which the handout left open. AC-24 and E2E-04 require navigating directly to another Requester's Ticket **by URL**, which needs real addressable routes — state-based view switching cannot express that test. It also gives the shell a genuine active-page indicator (`ui-spec.md` §7). Added as a dependency; the rest of the stack is unchanged. |
| **D-12** | Attachments are added from Ticket Detail immediately after creation, not inside the Create Ticket form | The handout §4.4 lists Attachments on the Create Ticket screen and Part 6 evidence exercises a valid and an invalid file there. FR-08 ("attach during ticket creation") is realised as part of the **intake flow** — Create Ticket saves the Ticket, and its success panel's **View ticket** action lands on Ticket Detail (#17), where the attachment lifecycle (upload, MIME/size validation, the five-file limit, download, soft removal) is built once. This follows directly from BR-48/D-08, which already make ticket creation and attachment upload **separate operations** so a long Description is never lost to a failed upload; a single multipart create-with-files form would contradict that compensation model and duplicate the upload UI across two screens. The Part 6 evidence (one valid + one invalid attachment) is therefore captured on this flow in Issue #17. Raised in the PR #24 peer review; recorded here so the deferral is an explicit assumption, not a silent gap. |

### Open assumptions

- Uploaded files are not virus-scanned. Out of scope for Lab 2; noted for Lab 3.
- Attachment previews are not rendered in-browser; download only.
- Timestamps are stored in UTC and rendered in the browser's local timezone.
